## Decision and falsifiable scope

Historical v1 recommendation, now withdrawn: review this small **trusted-host, single-model-server
behavioral baseline** before building its narrowly bounded HTTP composition. Keep the first campaign below 13 committed actions
per rollout and one outstanding model request. Do not add a generic scheduler, messaging system,
model hierarchy, continuing-successor mechanism or integrity cache to reach this baseline.

The proposed primary comparison is persistent, model-selected work against a strong scripted
coordinator under equal declared call/token/time ceilings and the same replacement schedule.
The result can be a null, regression, ceiling effect or infrastructure-limited campaign. This
baseline does not estimate epsilon-charity, train parameters, demonstrate emergent organization,
or establish competence at long horizons. Its verifiable outcome permits **PPRL-VR** for this
particular task; the broader program remains PPRL.

This proposal assumes trusted local serving and controller code. Accepting that narrower scope is
an outstanding review decision. It does **not** satisfy or silently waive the canonical independently
attested live-swarm gates in `pprl-epsilon-charity-program.md` and `pprl-four-fabric-architecture.md`.
Claims about adversarial model-serving containment, independent attestation or complete capture
remain unavailable even if a trusted-host baseline is later authorized.

## Task population and outcome authority

Reuse `AlgebraCorpusGenerator`, version `padawan-algebra-v1`, in the existing algebra domain.
One project contains six questions: two each from `linear_both_sides`, `omitted_branches` and
`extraneous_roots`. Each question comes from a different generated instance group; unused matched
siblings are excluded. Questions and groups are disjoint across all selected projects. Draw by the
fixed seed and rejection rule in the preparation script, with at most 1,000 candidate draws, without
examining any model output. There are 12 main projects and two separate calibration projects.

The 12 projects are the analysis clusters. Six questions within a project are related observations,
not six independent institutions; two stochastic replicates are nested within each project.
Sampling is without duplicate questions/groups from the finite generator population. The fixed
three-template coverage limits generalization; it is not broad mathematical or scientific research.
These are adaptive-development material, not a sealed challenge, training corpus or novelty test.
Public seeds and small algebra templates cannot establish absence from model pretraining.

The native corpus records retain their `curriculum` source-pool label; eventual PPRL executions
must explicitly bind `adaptive_development`. Neither that native label nor authored source rights
creates training eligibility or a cross-project memory permission.

The outcome is an exact complete real integer solution set for each question. The independent
`oracle` reads the original generated equation with three fixed grammars and solves it using integer
arithmetic. It does not use the generator's answer, SymPy, an external solver or a model response to
decide truth. Offline preparation cross-checks its solutions against the generator's independently
validated expected answers. All 84 selected questions must agree before the sample is frozen.

The untrusted response grammar is exactly `{"slot": 0, "values": ["-2", "4"]}`: a valid local
question index, one or two unique decimal integer strings in [-100,100], and no additional fields.
The 4 KiB reader rejects duplicate JSON keys, booleans, noninteger values, expressions, prose and
oversized/deep malformed input. It never passes model-authored expressions to `sympify`, `eval`,
shells or arbitrary tool execution. A malformed response consumes its actual call and counts as a
model failure; an unsupported trusted equation grammar is an infrastructure error and stops the run.

The existing `AlgebraGrader` checks equivalence between supplied steps and expected final answers,
but its API lacks the original task and therefore does not anchor the first step to that task.
This pilot deliberately declares final solution-set correctness as its authority. It makes no
verified-public-derivation claim. Missing branches and extraneous roots fail exact set equality.
No change to the production algebra grader is needed for this declared outcome.

## Conditions, public state and replacement

| Condition | Selection and worker-visible information | Roster |
| --- | --- | --- |
| `persistent_replacement` (P) | Model chooses a question; receives all six questions and this rollout's admitted candidate/verdict ledger | Two alternating logical clients; replace both after calls 4 and 8 commit |
| `scripted_coordinator_replacement` (C) | Same questions and admitted ledger; controller assigns an unsolved question with the fewest prior attempts, ties by slot | Same alternation and replacement as P |
| `no_history_replacement` (N) | Model chooses a question; receives questions and remaining budget only; previous candidates/verdicts are withheld | Same alternation and replacement as P |
| `single_worker_no_replacement` (S) | Same questions and admitted ledger as P; model chooses a question | One stable logical client for the rollout |

Use identical reviewed instructions, checkpoint, sampler, request ceilings, verifier and stop rule.
The exact instruction string is in the proposal. All conditions see only canonical allowlisted
observations. The planned registered public extension has `questions`, optional `attempts` with
numeric candidates and categorical verdicts, and optional `assigned_slot`. A trusted executor checks
the condition-specific action mask. No worker-controlled identifier acts as a command.

For C, choosing another slot consumes the call and records a model protocol failure. A malformed
attempt advances the controller's attempt count for its assigned slot; P/N/S malformed attempts
have no inferred slot. A solved slot remains solved. Repeating an identical candidate never earns
additional progress. Stop at six verified solutions, the call ceiling, any authority/health failure,
or the earliest resource bound. There is at most one final control transition per rollout.

Raw calls and complete retained verifier records stay private. Only a separate typed candidate/
verdict derivative may enter P/C/S state through a fixed reviewed, provenance-bearing admission
policy. N retains equivalent private accounting/evidence, without making its history worker-visible.
Never hydrate from raw model traffic, private reasoning, verifier source/answers, failure logs,
credential material, control IDs or discoverable forensic references. The preparation file's project
IDs and private sample metadata are researcher joins; only the questions enter model observations.

At a replacement boundary, finish and verify the committed action, stop and reap both owned client
processes, revoke their capabilities, discard their local caches/context, issue two new short-lived
capabilities, and deliver the current canonical observation. The rollout, task owner, original
grant, total budgets and condition remain fixed. No task is forked or resampled. Calibration's
two-call runs do not reach a scheduled replacement. No intentional crash is injected during inference.

S also has no unrecorded conversation, previous-response chain or private reasoning reuse. Thus P
versus S is primarily a controlled behavioral check on the replacement plumbing; with stateless
requests and paired seeds, equivalence is an expected and useful null. It cannot identify loss of
unmeasured worker memory. The shared serving engine is **not** replaced at client churn: per-request
KV state must drain and prefix caching is off. This tests logical-client replacement, not model-
process death, loaded-weight replacement or scientific continuity through server failure. Those
remain separate later experiments.

## Fixed sampling, order and analysis

The companion materializes 96 main rollouts: 12 projects × 4 conditions × 2 stochastic replicates.
Eight calibration rollouts use the two separate projects × four conditions × one replicate, with
two calls each. All 104 coordinates fit one 128-entry finite plan. The prepared schedule is a design
manifest, **not** an enrolled `ProcessTaskPlan` or Amber authorization; exact execution and initial-
state bindings must be compiled before any rollout exists in the eventual original authorization.

Main project/replicate blocks are shuffled by the frozen schedule seed. Within each block a rotated
random condition order counterbalances every condition across the four positions (six each).
Call seeds are paired across conditions for the same project/replicate/action index and differ
between replicates. Pairs do not make conditions independent. No checkpoint forks or cross-project
memory are used. A fixed generation policy is materialized for each declared call seed before the
campaign; a worker cannot alter it or request another draw.

Primary endpoint: proportion of projects with all six questions correctly solved within the declared
budget. Primary contrast: mean of the 12 within-project P-minus-C differences after averaging the two
replicates. Report every raw project/replicate result and a percentile 95% interval from 10,000
bootstrap resamples of entire project clusters, retaining all conditions and replicates together,
using the frozen analysis seed. With only 12 clusters and two replicates, this is exploratory precision;
there is no powered noninferiority, population-wide superiority or emergence claim.

Secondary, separately labeled contrasts are P-minus-N and P-minus-S. Report partial progress (unique
verified questions / six), wrong and malformed outputs, exact repeated `(slot, normalized candidate)`
frequency, redundant attempts on solved slots, progress after each replacement, recovery duration,
call count, total processed input/output tokens, elapsed time, retained bytes and all exclusions.
Useful negative-result reuse means fewer repeated previously rejected candidates in P than N; a
transcript describing cooperation does not establish that effect. Do not multiply action/question
counts into the effective sample size or select a favorable metric after seeing outcomes.

Ceilings and opportunities are matched; consumed tokens and information content are not identical.
N's observation is intentionally shorter, and early completion saves calls. Report actual usage and
the progress-versus-cumulative-token/call curves beside outcomes. Do not claim a benefit independent
of extra available context or compute from this pilot alone. Any subsequent padding, memory ablation,
compute-matched replay or epsilon/regret comparison requires its own preregistration.

Infrastructure interruptions and not-started tasks remain visible in the complete 104-row accounting.
For the main intention-to-run endpoint, success means retained verified completion; unknown and
not-started rows contribute no **verified success**, without being relabeled domain failures.
Also report observed-domain outcomes separately with their denominators and worst/best-case bounds
for missing main outcomes. Any missingness invalidates a clean comparative-success claim. No reruns,
replacement samples or budget refill repair missing outcomes within v1. Calibration is excluded from
all main estimates. Poor calibration output is reported; changing prompts/sampler/domain creates v2
before new main data, preserving v1's evidence and exclusions.
